CUDA Reduce 优化：从朴素树形规约到 Warp Shuffle

2026-10-03 #cuda 编程#Reduce

上一篇博客讨论了 CUDA 性能优化的基本方法：先确认瓶颈，再从 Warp、全局内存、共享内存、Occupancy 和同步等角度逐项分析。这次把这些知识集中到一个算子上：Reduce（规约）。

Reduce 看起来只是把一组数加起来，却同时包含了 GPU 编程中最典型的难题：输入很多、输出很少；线程之间需要交换中间结果；不同实现会产生分支分歧、共享内存冲突、空闲线程和不必要的同步。AIInfraGuide 的这篇文章从 V0 到 V7 逐步优化 CUDA Reduce，很适合作为理解“一个 Kernel 如何被持续打磨”的案例。

本文以 Sum Reduce 为主线，目标是计算：

S=∑i=0N−1xi.

文中性能数字来自教程给出的 A100 80GB SXM4、CUDA 12.x、N = 2^{27}（128M 个 float，约 512 MB）示例。它们不是本文在当前环境中的实测结果。不同 GPU、时钟、ECC、编译选项、输入数据和计时边界都会改变结果。

1. Reduce 为什么值得单独学习？

Reduce 是典型的“多输入到少量输出”算子。除了 Sum，还包括：

每个元素的读取和局部计算可以并行，但最终多个部分结果必须合并。串行循环需要大约 N - 1 次合并；二叉树形规约每轮把候选数量缩小一半，理论上只需要 O(log2 N) 层。

Reduce 的一个重要特征是算术强度低。对 Sum Reduce，每个元素大致需要一次 4 字节读取和一次加法：

I=1 FLOP4 Bytes=0.25 FLOP/Byte.

因此它通常是内存带宽受限的任务。优化重点不是让加法本身更复杂，而是：

  • 尽量合并地读取全局内存；
  • 减少无效线程和额外指令；
  • 让线程间通信走更合适的层次；
  • 减少屏障、循环控制和原子争用；
  • 让每次 Kernel 启动处理更多有效数据。

1.1 Reduce 的输出通常是分层产生的

1.2 正确性不只是“数值相等”

浮点加法不满足严格结合律：

(a+b)+c≠a+(b+c).

树形规约的加法顺序与 CPU 的线性循环不同，结果最后几位出现差异是正常的。测试时应：

  1. 用较高精度或可信库构造参考值；
  2. 同时使用绝对误差和相对误差；
  3. 检查 NaN 和 Inf；
  4. 对不同 Block 大小和不同优化版本分别验证。

如果 Sum Reduce 中包含正负数相消，误差可能比简单的全正输入更明显。性能提升不能以悄悄改变数值契约为代价。

2. V0：把每个 Block 搬到共享内存，再做朴素树形规约

2.1 思路

假设一个 Block 有 256 个线程：

  1. 每个线程从全局内存读取一个元素，写入共享内存；
  2. step = 1 时，线程 0 加线程 1，线程 2 加线程 3；
  3. step = 2 时，线程 0 加线程 2，线程 4 加线程 6；
  4. 步长不断翻倍，直到线程 0 保存整个 Block 的和。

2.3 V0 的第一个瓶颈：Warp Divergence

GPU 以 Warp 为重要的执行单位。V0 的判断条件是：

同一个 Warp 中有些线程满足条件，有些线程不满足，硬件需要用不同活跃掩码执行路径。以 256 线程 Block 为例：

Step 活跃线程 直观问题
1 tid = 0, 2, 4, ... 一个 Warp 中约一半线程有工作
2 tid = 0, 4, 8, ... 更多 lane 空闲
4 tid = 0, 8, 16, ... 工作线程更加稀疏
更大 step 少量低编号线程 大多数线程只等待同步

教程在特定 A100 环境中测得 V0 带宽利用率约 15%，但这个数字不应当被当作所有机器的固定结果。这里真正值得学习的是访问模式：活跃线程在 Warp 中交错出现，导致分歧和低利用率。

3. V1：改变线程映射，减少分支分歧

3.1 用连续线程表示连续工作

V1 仍然从小步长向大步长迭代，但把判断改成：

在 step = 1、blockDim = 256 时，线程 0～127 整体进入分支，线程 128～255 整体跳过。前四个 Warp 不分歧，后四个 Warp 也不分歧。只有当活跃线程数少于一个 Warp 后，Warp 0 内才会出现部分 lane 活跃。

V1 的经验是：线程映射本身就是性能设计的一部分。 同样的数学运算，换一种线程与数据的对应关系，就可能改变 Warp 分歧和内存访问模式。

3.2 V1 仍然不够好

V1 减少了控制流分歧，但它从小步长开始时，活跃线程访问的共享内存地址间隔较大。以 Warp 0 的部分线程为例，可能同时访问 shared[0]、shared[32]、shared[64] 等地址。它们映射到同一个 Bank 的不同地址时，会产生 Bank Conflict。

所以，消除了一个瓶颈，不代表 Kernel 已经接近最佳状态。下一步需要重新画出每个 Warp 在共享内存中的地址。

4. V2：反转规约方向，同时改善 Bank Conflict

4.1 共享内存的 Bank 访问模型

在常见 32 位共享内存模式中，可以把 Bank 编号近似理解为：

bank=(byte address4)mod32.

同一个 Warp 的线程访问 32 个不同 Bank 时，可以并行服务；访问同一个 Bank 的不同地址时，请求可能串行化。多个线程读取同一个地址通常可以广播，不属于同一种冲突。

4.2 从大步长向下折半

V2 使用经典的“连续线程、步长减半”模式：

以 256 线程为例，第一轮 step = 128，线程 0～127 工作，正好是连续的四个 Warp。每个 Warp 中的线程分别访问相邻地址，访问模式规整；后续 step = 64、32、16... 继续保留低编号的连续活跃线程。

V2 同时改善了两件事：低编号线程连续活跃，减少 Warp 分歧；相邻线程访问连续共享内存，减少典型 Bank Conflict。教程在示例硬件上给出的带宽利用率约为 40%。

4.3 为什么 Bank Conflict 不能只看数组声明？

__shared__ float shared[256] 本身没有“好”或“坏”的访问模式。冲突取决于同一条指令中一个 Warp 的 32 个线程访问哪些下标。

矩阵转置里经常使用 tile[32][33] 的 Padding，是因为列访问会让多个线程落入相同 Bank；一维 Reduce 的 V2 则主要通过改变规约方向和线程下标，让访问自然连续。两种场景的解决方法不同，不能机械套用 Padding。

5. V3：每个线程先处理两个元素

5.1 V2 中的一半线程很快会闲置

V2 每个线程只加载一个元素。第一轮规约后，Block 中只有一半线程继续参与；后续轮次中活跃线程越来越少。另一半线程在加载阶段做过一次搬运，之后大部分时间只是等待屏障。

V3 不减少每个 Block 的规约轮数，却让每个 Block 处理两倍输入，减少了 Block 数量和调度开销，并让加载阶段的线程做了更多有用工作。教程示例中的带宽利用率约为 45%。

每线程处理两个元素不是越多越好。继续增加元素数量可能增加寄存器压力、降低 Occupancy、拉长单线程依赖链，甚至让内存访问并行度下降。应通过实验比较 1、2、4 等处理粒度。

6. V4：展开最后一个 Warp

6.1 最后一个 Warp 不需要 Block 屏障

V3 的循环在 step = 128、64、32、16、8、4、2、1 都调用 __syncthreads()。当 step <= 32 时，只有线程 0～31 还在执行加法，也就是一个 Warp。若这 32 个线程走同一个规约路径，Block 级屏障已经没有必要。

7.1 运行时循环还有固定开销

V4 的前几轮仍然有循环变量更新、比较、跳转和边界判断。如果 Block 大小在调用点已经选择为 128、256 或 512，那么这些轮次其实是已知的。

8. V6：用 Warp Shuffle 替换 Warp 内共享内存

8.1 Warp 内规约

__shfl_down_sync 让当前线程读取同一 Warp 中更高 lane 的寄存器值：

相比通过共享内存交换值，Shuffle 不需要为 Warp 内的每一步单独写入和读取共享内存，也不需要把 Warp 内规约写成多轮 Block 屏障。

8.2 两级规约

Shuffle 只能在一个 Warp 内工作。256 线程 Block 有 8 个 Warp，因此通常分两层：

  1. 每个 Warp 用 Shuffle 得到一个 Warp sum；
  2. 每个 Warp 的 lane 0 把结果写入共享内存；
  3. 第一个 Warp 读取这些 Warp sums，再用 Shuffle 得到 Block sum；
  4. Block 的线程 0 写出 partial sum。

对于常见的完整 Block 和尾部用 0 填充场景，也可以使用完整 Warp 掩码。这里展示动态掩码，是为了强调 Shuffle 的参与线程必须和算法实际一致。使用掩码时，要保证被命名的参与线程都能执行同一个 Warp 原语；不能只让一个分支中的线程调用，却把掩码写成全 Warp。

V6 的优势来自减少共享内存访问和同步，而不是让全局读取消失。它仍然需要一次 Warp 间的共享内存交换和一次 Block 屏障。教程给出的示例带宽利用率约 72%。

8.3 Warp Shuffle 版本的通用边界

  • Block 大小最好是 Warp 大小的倍数；否则最后一个 Warp 的掩码与 Warp 数需要特别处理。
  • __shfl_down_sync 的源 lane 必须存在于参与掩码中，或由算法保证读取结果不会被使用。
  • Shuffle 只交换寄存器值，不能替代 Block 级同步，也不能让不同 Block 互相通信。
  • 对 Max、Min、乘法等 Reduce，只需要替换规约运算和单位元，但要考虑 NaN 规则。
