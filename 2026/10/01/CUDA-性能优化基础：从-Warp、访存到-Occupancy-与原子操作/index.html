CUDA 性能优化基础：从 Warp、访存到 Occupancy 与原子操作

2026-10-01 #cuda 编程

在上一篇 [CUDA 编程初探] 中，我们用向量加法走通了 CUDA 程序的基本流程：分配显存、搬运数据、启动 Kernel、校验结果和测量时间。程序能够正确运行之后，下一个问题自然是：它为什么还不够快？

CUDA 优化很少是“换一个更复杂的写法就会更快”。一个 Kernel 可能在等待全局内存，也可能因为同一 Warp 内的线程走了不同分支而浪费执行槽；可能是寄存器和共享内存限制了可驻留的 Warp，也可能是大量线程争用同一个原子变量。只有先找出限制因素，优化才有方向。

本文基于 AIInfraGuide 的 CUDA 性能优化基础概览、Warp 与执行模型、内存访问优化、Occupancy 与资源分配、同步与原子操作 五篇文章重新整理。正文不追求记住一串固定数字，而是建立一条可以反复使用的思考路径：

保证正确 → 建立基线 → 找到瓶颈 → 只改一个变量 → 重新验证结果与性能。

文中的性能数字如果没有明确说明，均用于解释原理，不代表本文作者的实测结果。GPU 架构、CUDA 版本、编译器和输入规模都会改变实际表现。

1. 性能优化首先是一套实验方法

优化前，先把“快”定义清楚。至少需要区分下面几种时间：

指标 包含的工作 适合回答的问题
Kernel 时间 GPU 上某个 Kernel 的执行区间 Kernel 本身是否变快？
GPU 流水线时间 H2D、多个 Kernel、D2H 等指定阶段 整段 GPU 工作是否变快？
端到端时间 CPU 准备、分配、传输、GPU 计算、同步和后处理 应用实际是否受益？

只比较 Kernel 时间，可能忽略 PCIe 传输；只看端到端时间，又可能掩盖 Kernel 内部的变化。两种数据都可以记录，但计时边界必须一致。

一个可靠的实验至少要做到：

  1. 使用相同输入，先比较 CPU 或可信库的参考结果。
  2. 检查 NaN、Inf，并根据算法选择合理的绝对误差和相对误差。
  3. 使用 Release 优化编译，记录 GPU、驱动、Toolkit、编译参数和数据规模。
  4. 预热后重复测量，报告中位数或稳定的统计结果。
  5. 一次只改变一个主要因素，例如 Block 大小或数据布局。
  6. 优化后重新做正确性检查，因为数据竞争有时只在特定调度下暴露。

工具的分工也很清楚：Nsight Systems 用时间线回答“CPU、传输和 Kernel 在什么时候运行”，Nsight Compute 深入一个 Kernel，回答“它为什么花这么久”。分析前可以先编译带设备行号的优化版本：

-G 会生成设备调试代码并显著影响优化，因此不应拿调试构建做正式性能比较。

2. Warp：理解 GPU 实际怎样执行线程

2.1 Thread 是编程视角，Warp 是执行视角

我们编写的是单个线程的标量代码，但当前 NVIDIA GPU 会把一个 Block 中线性线程编号连续的线程组成 Warp，每个 Warp 包含 32 个 lane。

warpSize 在 CUDA 设备代码中表示 Warp 宽度；为理解当前 NVIDIA CUDA GPU，可以认为它是 32。一个 256 线程的 Block 因而包含 8 个 Warp。Block 大小不是 32 的倍数时，最后一个 Warp 仍占用调度资源，只是部分 lane 没有对应线程。

SM 上会驻留多个 Warp。一个 Warp 因内存依赖或指令依赖暂时不能继续时，Warp Scheduler 可以发射另一个已就绪 Warp 的指令，以此隐藏延迟。这种切换不需要像 CPU 操作系统线程那样保存和恢复上下文，因为驻留 Warp 的状态已经保存在 SM 资源中。

这里的关键不是“线程越多越好”，而是调度器在多数周期里能否找到有资格且已就绪的 Warp。

2.2 SIMT 与分支分歧

SIMT（Single Instruction, Multiple Threads）让我们用独立线程来表达程序，同时让一个 Warp 的活跃 lane 执行共同的指令。当同一个 Warp 中的线程需要走不同控制流路径时，硬件会用活跃掩码执行这些路径，某条路径之外的 lane 暂时不参与。这就是 Warp Divergence。

分歧发生在同一个 Warp 内。如果 Warp 0 全部执行 A、Warp 1 全部执行 B，这两个 Warp 可以独立调度，不构成同一个 Warp 内的分歧：

不能简单断言一个 if/else 一定慢 2 倍，或者最坏一定慢 32 倍。真实代价取决于各路径的指令数量、内存访问、编译器是否使用 predication、分支数据分布，以及路径能否很快重新汇合。优化前应查看分支与活跃线程相关指标，而不是只凭源码中的 if 做判断。

3. 内存访问：先减少无效流量，再谈更复杂的计算

3.1 用 Roofline 建立上限意识

算术强度定义为完成算法所需的计算量与数据流量之比：

I=FLOPsBytes.

给定峰值计算吞吐 Ppeak 和峰值内存带宽 Bpeak ，Roofline 给出的理想性能上界是：

P≤min(Ppeak, Bpeak×I).

向量加法每个元素做一次加法，按算法流量读两个 float、写一个 float，算术强度约为 1 / 12 = 0.083 FLOP/Byte，通常属于带宽受限任务。此时把一次加法换成更短的表达式不会产生明显收益；更值得检查的是实际传输了多少数据、访问是否合并，以及中间结果能否复用。

Roofline 是上界模型，不是对每个 Kernel 的自动分类器。小 Kernel 可能受启动延迟限制，不规则 Kernel 可能受访存延迟而非饱和带宽限制，原子争用和依赖链也可能成为真正瓶颈。

向量化可能把多条窄加载指令合成更少的宽加载指令，减少指令和地址计算压力。它没有减少算法总字节数，也不会保证 DRAM 带宽自动提高；有时编译器已经生成合适指令，有时更宽的每线程数据还会增加寄存器压力。因此仍要检查生成代码和实际耗时。

4. Occupancy：它衡量驻留能力，不直接衡量速度

4.1 定义与作用

Occupancy 的常见定义是：

Occupancy=每个 SM 的活跃 Warp 数每个 SM 支持的最大 Warp 数.

这里的“活跃”通常表示 Warp 已驻留在 SM 上，而不是说它当前周期一定正在执行。理论 Occupancy 根据启动配置和静态资源需求计算；Achieved Occupancy 则是运行时观测值。两者都不能直接替代 GPU 利用率、吞吐量或耗时。

Occupancy 的主要价值是为延迟隐藏提供候选 Warp。当一个 Warp 等待全局内存时，调度器可以从其他已就绪 Warp 中选择工作。如果驻留 Warp 太少，调度器更容易找不到可发射指令的 Warp。

但是更多驻留 Warp 只是增加机会。若所有 Warp 都在等待同一种长延迟操作，或者 Kernel 已经达到带宽上限，提高 Occupancy 未必继续加速。

4.2 哪些资源限制驻留 Block？

一个 Block 必须作为整体驻留到某个 SM。能同时驻留多少个 Block，要同时满足多种约束：

  • 每个 SM 的最大线程数与最大 Warp 数；
  • 每个 SM 的最大驻留 Block 数；
  • 每线程寄存器数乘以 Block 线程数，并考虑分配粒度；
  • 每个 Block 的静态及动态共享内存，并考虑分配粒度；
  • 架构和 Kernel 自身的启动限制。

可以把可驻留 Block 数写成概念公式：

Bactive=min(Bthread,Bwarp,Bregister,Bshared,Barchitectural).

随后：

Wactive=Bactive×⌈Tblock32⌉.

手算有助于理解，但寄存器和共享内存分配存在架构相关的粒度与限制。最终应使用 CUDA Occupancy API、编译器资源报告和 profiler，而不是把某一代 GPU 的固定表格套到所有设备。

4.4 为什么 Occupancy 不是越高越好？

寄存器和共享内存不仅是限制条件，也是提高单个 Warp 效率的资源：

  • 更多寄存器可以保存更多累加器，增加指令级并行度，减少中间值访存；
  • 更大的共享内存 Tile 可以增加数据复用，减少全局内存流量；
  • 较大的每线程工作量可以摊薄索引和循环开销。

如果为了追求 100% Occupancy 而强制减少寄存器，编译器可能把值 spill 到 Local Memory。Local Memory 是线程私有地址空间，但通常由设备内存承载并经过缓存，延迟远高于寄存器。此时 Occupancy 上升，性能反而下降。

-maxrregcount 和 __launch_bounds__ 可以影响编译器的资源决策，但应作为实验参数使用：

这里的第二个参数表达希望每个 SM 至少容纳的 Block 数，编译器会据此权衡寄存器使用。它不是运行时保证，也不能替代性能测量。

4.5 一套更实用的 Block 大小实验

对于简单一维 Kernel，可以从 {128, 256, 512} 开始扫描：

  1. 每个配置使用相同输入和 Grid 覆盖策略。
  2. 记录 Kernel 时间、理论/实际 Occupancy、寄存器、共享内存和 spill。
  3. 查看内存吞吐、Eligible Warps 与主要 Stall 原因。
  4. 保留实际最快且结果正确的配置。

小 Block 可能受到每 SM 最大 Block 数限制，大 Block 可能因寄存器或共享内存导致同驻留 Block 减少。最优点取决于 Kernel 和 GPU，没有跨设备永久有效的固定答案。

5. 同步：屏障、内存顺序与原子性是三件事

并行程序中的错误常来自把三个概念混在一起：

概念 解决的问题 典型工具
屏障（Barrier） 参与线程是否都到达某个阶段？ __syncthreads()、__syncwarp()
内存顺序与可见性 某次写入何时能被指定范围观察？ 屏障的内存语义、Fence、现代原子内存序
原子性 多线程读改写同一地址是否丢失更新？ atomicAdd、atomicCAS 等

Fence 不会让其他线程停下来等待，原子操作也不自动成为整个 Block 的屏障。选择原语前，应先说清楚需要的是哪一种保证。

5.4 Memory Fence 只处理顺序，不负责等待

传统 CUDA Fence 有不同作用域：

它们约束调用线程的内存操作顺序与相应范围的可见性，但不会让其他线程等待到这里。要实现“写数据，然后发布完成标志”，还需要配合原子标志或其他同步协议；接收方也必须使用匹配的观察方式。

跨 Block 通信尤其容易写错，还可能出现前向进展问题。若没有强烈的单 Kernel 融合需求，分成多个 Kernel 往往更清楚。现代 CUDA 还提供带作用域与内存序的原子 API，复杂生产代码应优先依据目标 CUDA 版本的官方内存模型设计，而不是只靠经验拼接 volatile、Fence 和计数器。

6. 原子操作：正确并不代表可扩展

6.1 为什么普通 += 会丢失更新？

counter += 1 通常包含读取、加法、写回三个步骤。如果两个线程同时读取旧值 5，再各自写回 6，最终只增加一次。

原子操作把目标地址上的读改写作为不可分割操作，从而防止丢失更新。它保证的是该地址上的操作原子性，不保证多个不同地址组成的更大事务也是原子的。

支持的操作与数据类型随计算能力和 CUDA 版本变化。例如 double 的原生 atomicAdd 有架构要求，使用前应检查目标设备，而不是依赖一张脱离版本的固定列表。

6.2 性能取决于地址争用程度

若线程原子更新彼此不同的地址，可以保持较高并行度；如果成千上万线程竞争一个地址，操作就会在该地址上串行化。

数据分布偏斜时，热门 bin 会产生严重争用。常见改法是每个 Block 在共享内存中维护局部直方图，处理完一批输入后再合并到全局结果。这样把大量全局争用变成片上争用和少量全局更新。

但局部直方图也不是免费方案：bin 数过大时，共享内存用量会降低 Occupancy；初始化与合并也有成本；共享内存原子仍可能争用。更进一步可以为每个 Warp 或线程维护私有副本，但寄存器和共享内存开销会增加。这正是原子优化与 Occupancy 互相影响的地方。

7. 四类优化其实相互制约

这些主题不能孤立看待：

例如，扩大矩阵乘法 Tile 可以提高数据复用，却增加共享内存与寄存器，Occupancy 可能下降；把每线程的四次加载改成 float4 可能减少指令，却增加寄存器活跃区间；把全局原子改成 Block 局部直方图减少了争用，却可能占用大量共享内存。

因此，优化目标是让整条关键路径更短，而不是让某个单独指标看起来更漂亮。

8. 把方法用回前一篇的练习代码

8.1 向量加法与 SAXPY

这两类 Kernel 算术强度低，可以按下面顺序实验：

  1. 确认相邻线程访问相邻元素，计算有效带宽。
  2. 扫描 128、256、512 三种 Block 大小。
  3. 用 Grid-stride Loop 控制 Grid 数量，并确保并行度足够。
  4. 在地址对齐、尾部处理正确的前提下测试 float4。
  5. 检查向量化是否真的减少指令，以及寄存器与耗时是否变化。

若数据每次都从 CPU 搬到 GPU，再搬回来，端到端性能还会受传输限制。此时 Kernel 微优化的收益可能被淹没，应考虑数据驻留与多算子融合。

8.2 点积

前一篇的 dot_product.cu 使用纯共享内存树形规约。可以构造三个版本进行对比：

  • 版本 A：当前每轮 __syncthreads() 的共享内存规约；
  • 版本 B：每个 Warp 用 Shuffle 规约，只把 Warp 结果写入共享内存；
  • 版本 C：每线程先用 Grid-stride Loop 或向量化加载累加多个元素，再执行版本 B 的 Block 规约。

每个版本都要记录寄存器、共享内存、理论/实际 Occupancy、Kernel 时间和数值误差。规约顺序改变后，浮点结果最后几位发生变化并不意外。

当前点积代码把 65,536 个 Block 部分和拷回 CPU 再求和。若要完整比较 GPU 方案，还应增加第二阶段 GPU 规约，并分别测量 Kernel 阶段与完整流程。

8.3 异步分块程序

前一篇已经说明：同一个 Stream 中的 H2D、Kernel、D2H 仍按依赖顺序执行。多 Stream 分块后，可以用 Nsight Systems 验证复制引擎与计算是否真的重叠。

这时应同时检查：

  • 每块数据是否足够大，能够摊薄启动和提交开销；
  • 主机缓冲区是否使用锁页内存；
  • 不同 Stream 是否使用互不冲突的数据区间；
  • 最终等待是否放在所有任务提交之后；
  • 多 Stream 是否因 Kernel 资源占用或带宽竞争而没有获得收益。

9. 一张可执行的优化检查表

面对一个慢 Kernel，可以沿着下面的顺序检查：

阶段 要问的问题 常见行动
正确性 是否有越界、数据竞争、错误掩码或错误屏障？ Compute Sanitizer、参考结果、异常值检查
系统时间线 时间花在 CPU、传输还是 Kernel？ Nsight Systems、明确计时边界
瓶颈类型 启动、内存、计算、依赖、同步还是原子争用？ Nsight Compute、Roofline、Stall 分析
Warp 是否有低效分支或部分 Warp？ 重排任务、调整 Block、正确使用 Warp 原语
全局内存 相邻线程是否访问相邻地址？是否搬了无用数据？ 改布局、合并访问、减少中间流量
共享内存 是否真正复用数据？是否有 Bank Conflict？ Padding、调整 Tile、减少屏障
Occupancy 哪种资源限制驻留？提高它是否能改善延迟隐藏？ 扫描 Block、检查寄存器/smem/spill
原子操作 是否大量线程竞争相同地址？ 私有化、Warp/Block 聚合、多阶段归约
验证 优化是否真的改善目标指标？ 重复基准、复查结果、保留实验记录

真正有价值的性能结论应能够回答三件事：原版本受什么限制；修改改变了哪项硬件行为；测量结果是否与这个解释一致。

10. 小结

Warp 解释了线程如何以 32 个 lane 为一组执行，也解释了分支、Shuffle 和 Vote 原语的行为。内存优化要求从 Warp 的地址集合出发，减少 sector 流量、Bank Conflict 和重复搬运。Occupancy 描述 SM 能驻留多少 Warp，主要用于理解延迟隐藏，但不等于性能。同步、Fence 和原子操作分别解决阶段协调、内存顺序与读改写冲突，不能互相替代。

当这些知识连在一起时，CUDA 优化就不再是一组零散技巧，而是一套基于证据的过程：观察执行行为，找出限制因素，在资源、复用和并行度之间做权衡，然后用正确性与性能数据验证结论。
